# US-05: Chọn danh mục và thấy ảnh mình mặc sản phẩm đầu tiên

## Bối cảnh
- Epic: Phòng thử đồ (Epic 3).
- Vai trò: Người mua (user đã đăng nhập; admin cũng dùng được).
- Mục tiêu: Khi chọn một danh mục, thấy ngay hình ảnh CHÍNH MÌNH mặc sản phẩm đầu tiên của danh mục đó, do GenAI tạo từ ảnh toàn thân (US-02) và ảnh flat lay (US-04).

## Phạm vi
- Trang `/try-on`: chọn danh mục (chỉ danh mục có ≥ 1 sản phẩm – Q8).
- Trang `/try-on/:categoryId`: hiển thị sản phẩm đầu tiên (thứ tự `created_at asc, id` – D24) và ảnh thử đồ của user.
- Kiểm tra điều kiện: có ảnh toàn thân, chiều cao, cân nặng (Q13); đã đồng ý xử lý ảnh (Q14).
- Sinh ảnh bất đồng bộ (202 + polling), cache theo (user, sản phẩm, đầu vào), hạn mức ngày, provider adapter với `stub` mặc định, provider thật Gemini (Q12 đã chốt 2026-11-17), prompt cố định ở backend (người dùng không nhập prompt).
- Dọn kết quả khi user thay/xoá ảnh toàn thân hoặc admin thay ảnh/xoá sản phẩm.
- Ngoài phạm vi: chuyển sản phẩm (US-06), thêm vào giỏ (US-07, Sprint 4), gợi ý size theo số đo, chia sẻ/tải ảnh, lịch sử ảnh đã thử, tìm kiếm/lọc trong danh mục, nhiều ảnh kết quả cho một sản phẩm.
- Thiết kế chi tiết: `design/flows/try-on-room.md`; bảng/bucket `design/database/schema.md` mục 13–14; API tóm tắt `design/flows/README.md` mục 3.

## Luồng chính (happy path)
1. User đã đăng nhập, hồ sơ đủ, bấm "Phòng thử đồ" ở header → `/try-on` → client gọi `GET /api/categories` → lưới thẻ danh mục.
2. Chọn "Váy" → `/try-on/<id>` → lần đầu: hộp thoại đồng ý → "Đồng ý" → `POST /api/try-on/consent`.
3. Client gọi `GET /api/categories/:id/products` → sản phẩm đầu tiên → `POST /api/try-on { productId }`.
4. Chưa có cache → 202 `processing` → UI hiện trạng thái "Đang tạo ảnh bạn mặc {tên}…" (ảnh flat lay + bộ đếm giây) → poll `GET /api/try-on/:id` mỗi 2 s → `succeeded` → hiện ảnh 3:4, tên, giá, "1/N".
5. Lần sau vào lại cùng sản phẩm (đầu vào không đổi) → POST trả 200 `succeeded` ngay, không trừ lượt.

## Luồng lỗi cần xử lý
- Chưa đăng nhập / token hết hạn → `/login?redirect=/try-on...` (401, xử lý chung của `apiClient`).
- Thiếu ảnh toàn thân hoặc số đo → màn "Hoàn thiện hồ sơ" liệt kê mục thiếu + nút tới `/profile` (client), server 409 `PROFILE_INCOMPLETE` với `fields`.
- Chưa đồng ý → hộp thoại đồng ý; "Để sau" → quay lại `/try-on`. Server 409 `TRY_ON_CONSENT_REQUIRED`.
- Không có danh mục nào có sản phẩm → trạng thái rỗng "Chưa có sản phẩm để thử".
- `:categoryId` sai / không tồn tại → toast "Danh mục không còn tồn tại." và về `/try-on`; danh mục rỗng (vào bằng URL) → trạng thái rỗng + link chọn danh mục khác.
- Sản phẩm bị xoá giữa chừng (404 `PRODUCT_NOT_FOUND`) → tải lại danh sách sản phẩm.
- Sinh ảnh thất bại (`failed`: `GENERATION_FAILED`, `GENERATION_TIMEOUT`, `INPUT_REJECTED`, `PROVIDER_UNAVAILABLE`) → khối lỗi trong khung ảnh với `error.message` + nút "Thử lại"; vẫn hiện ảnh flat lay, tên, giá. `INPUT_REJECTED` kèm link "Đổi ảnh toàn thân".
- Client chờ quá 120 s → coi như lỗi timeout, nút "Thử lại".
- Hết hạn mức ngày → 429 `TRY_ON_QUOTA_EXCEEDED`: thông báo hết lượt + giờ reset; vẫn xem ảnh đã tạo và flat lay.
- Provider chưa cấu hình → 503 `TRY_ON_UNAVAILABLE`; quá nhiều request → 429 `TOO_MANY_REQUESTS`; lỗi mạng/500 → khối lỗi + Thử lại.
- Signed URL ảnh kết quả hết hạn (`<img onError>`) → GET lại một lần; vẫn lỗi → khối lỗi.

## Dữ liệu & validate
- `productId`: bắt buộc, uuid, sản phẩm tồn tại (400 `fields.productId` / 404).
- Điều kiện hồ sơ: `avatar_path`, `height_cm`, `weight_kg` khác null; `try_on_consent_at` khác null.
- Ảnh đầu vào: ảnh toàn thân và ảnh flat lay hiện tại (snapshot path lúc tạo job); backend tải từ Storage, gửi provider dạng base64.
- Ảnh kết quả: kiểm tra magic bytes jpeg/png/webp, ≤ 10 MB; lưu `try-on-results/{profile_id}/{product_id}/{id}.{ext}`; client nhận signed URL TTL 3600 s.
- Hạn mức: `TRY_ON_DAILY_LIMIT` (mặc định 30) job không `failed` / user / ngày giờ VN.

## API
Chi tiết: `design/flows/try-on-room.md` mục 4, 6, 7.

| Method | Path | Kết quả |
|--------|------|---------|
| GET | `/api/categories` | 200 `{ categories }` (đã có – Sprint 2) |
| GET | `/api/categories/:id/products` | 200 `{ category, products }` (đã có – Sprint 2) |
| POST | `/api/try-on/consent` | 200 `{ profile }` (idempotent) |
| POST | `/api/try-on` `{ productId }` | 200 `{ tryOn, quota }` (cache / đang chạy) · 202 `{ tryOn, quota }` · 400 · 404 · 409 · 429 · 503 |
| GET | `/api/try-on/:id` | 200 `{ tryOn }` · 404 `TRY_ON_NOT_FOUND` |
| GET | `/api/try-on/quota` | 200 `{ quota }` |

## Acceptance Criteria (kết hợp sprint backlog Task 2–4)
- User hồ sơ đủ, đã đồng ý, chọn danh mục → thấy ảnh mình mặc **sản phẩm đầu tiên** (thứ tự cũ nhất trước) kèm tên, giá "199.000 ₫", vị trí "1/N"; trong lúc chờ có trạng thái đang tạo rõ ràng.
- Với `stub`: ảnh hiện trong ≤ 5 s và có nhãn "Ảnh mô phỏng". Với provider thật (Task 6): p95 thời gian tới khi có ảnh ≤ 30 s (đo và ghi lại).
- Gọi lại cùng sản phẩm khi đầu vào không đổi → 200 ngay, không tạo row mới, `quota.used` không tăng. Hai request song song cùng sản phẩm → chỉ 1 job.
- Thay ảnh toàn thân → lần thử tiếp theo sinh ảnh mới từ ảnh mới; rows và object kết quả cũ của user bị xoá.
- Xoá ảnh toàn thân → mọi kết quả của user bị xoá; vào phòng thử đồ hiện màn "Hoàn thiện hồ sơ".
- Admin thay ảnh / xoá sản phẩm → object kết quả của sản phẩm đó bị xoá (`storage.objects` bucket `try-on-results` không còn object thừa).
- User A không xem được kết quả của user B (GET id của B → 404). Response không chứa `*_path`, `input_key`, tên provider.
- Hồ sơ thiếu / chưa đồng ý / hết lượt / lỗi sinh ảnh đều có màn hoặc thông báo hướng dẫn cụ thể, không lộ chi tiết kỹ thuật.

## Phi chức năng
- Bảo mật & riêng tư: ảnh toàn thân và ảnh kết quả là dữ liệu nhạy cảm – bucket private, signed URL 1 giờ, chỉ chủ sở hữu; gửi bên thứ ba (Google Gemini API, khi `TRY_ON_PROVIDER=gemini`; tier trả phí) chỉ sau khi đồng ý; `GEMINI_API_KEY` chỉ ở backend; không log ảnh/base64/URL ký/số đo/phản hồi thô của provider.
- Chi phí: `stub` mặc định ở dev/test/CI; hạn mức ngày + limiter; cache tránh sinh lại.
- Hiệu năng: POST/GET trả < 500 ms (không chờ provider); poll 2 s; giới hạn job đồng thời `TRY_ON_MAX_CONCURRENCY`.
- Độ bền: job treo do restart bị đánh dấu `failed` sau ngưỡng; người dùng bấm Thử lại được.
- UX/A11y: trạng thái đang tạo có chữ (không chỉ spinner), `aria-live` báo khi xong; desktop + mobile 375px không cuộn ngang; `prefers-reduced-motion`.
